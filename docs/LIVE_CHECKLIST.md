# Контролируемый переход к LIVE (этап 9)

Реальная торговля **не включается автоматически** и не включена в этой поставке. Ниже — порядок
действий, если вы решите её включить. Каждый пункт — обязательное условие, а не рекомендация.

## A. Условия, которые проверяет сама система

LIVE не включится, пока не выполнено всё:

1. На сервере задано `ALLOW_LIVE_TRADING=true` (по умолчанию `false`).
2. Стратегия получила `PASSED` в walk-forward на **реальных** данных (синтетика не считается; любое
   изменение параметров сбрасывает статус).
3. Терминал сообщает тип счёта `REAL`. При неизвестном типе LIVE запрещён.
4. Admin вводит пароль повторно и фразу `ENABLE LIVE TRADING`.
5. При работе через мост на Windows-хосте задано `BRIDGE_ALLOW_REAL=true` (иначе мост отклоняет ордера
   на реальном счёте).
6. После смены режима агент на паузе: нужен отдельный **Start**.
7. После перезапуска раннера LIVE восстанавливается только при выполненных условиях 1–3, и агент
   остаётся в PAUSED (если не задан `AGENT_AUTO_RESUME=true`, что для LIVE не рекомендуется).

## B. Что сделать вам до включения

- [ ] Walk-forward на 2–3 годах реальной истории брокера с его спредом и комиссией: статус `PASSED`.
- [ ] Forward-тест на демо **не меньше 4–8 недель** с той же версией стратегии и настройками;
      результаты демо сопоставимы с OOS-бэктестом (отчёт *Trade history → Demo*).
- [ ] На демо проверены сбои: разрыв связи, перезапуск с открытой позицией, ручное закрытие,
      Emergency stop. В журналах нет `CRITICAL` без объяснения.
- [ ] Проверена калибровка AI (`/api/ai/quality/`): Brier score и доля прибыльных по корзинам оценок.
- [ ] Имена символов, `volume_min`/`volume_step`, stops level, режимы заполнения брокера сверены
      с журналом исполнений на демо.
- [ ] Отдельный реальный счёт **с суммой, потерю которой вы готовы принять**. Не основной счёт.
- [ ] Лимиты на первое время **ниже демо-значений**: например, 0.25% на сделку, 1% открытого риска,
      1% дневного убытка, максимум 1–2 позиции.
- [ ] Сервер и мост доступны только через TLS/VPN; сильные пароли; `DJANGO_DEBUG=false`;
      `DJANGO_SECURE_HTTPS=true`; резервное копирование PostgreSQL.
- [ ] Мониторинг: кто-то смотрит дашборд и журналы; понятно, кто и как нажимает Emergency stop.
- [ ] Записан план отката: Emergency stop → решение по открытым позициям вручную → режим ANALYSIS.

## C. Включение

1. Режим DEMO → Stop. Обновите `.env` (`ALLOW_LIVE_TRADING=true`, `BRIDGE_ALLOW_REAL=true` на мосту),
   перезапустите backend, раннер и мост.
2. Переключите терминал на реальный счёт. Убедитесь в *Connection*, что тип счёта `real`.
3. *Risk management*: выставьте уменьшенные лимиты.
4. *Connection → Trading mode → Live*: пароль и фраза. Проверьте в *System logs* запись о смене
   режима и в аудите — кто её сделал.
5. **Start.** Первые сделки сверяйте вручную с терминалом: объём, SL, TP, комиссия.

## D. Когда немедленно остановиться

Emergency stop и возврат в ANALYSIS, если: результат заметно хуже OOS-бэктеста и демо; появилось
событие `UNKNOWN`/`CRITICAL` в исполнении; расхождение позиций журнала и терминала; брокер изменил
условия (спред, комиссия, маржа); сработал дневной лимит два дня подряд.

## Безопасный запуск: краткий чек-лист

- [ ] `.env` заполнен, секреты не в репозитории, `DJANGO_DEBUG=false`.
- [ ] `ALLOW_LIVE_TRADING=false`, `BRIDGE_ALLOW_REAL=false` (для демо-этапа).
- [ ] `python manage.py migrate && python manage.py bootstrap_roles`.
- [ ] Отдельные учётные записи с минимальными ролями (viewer / operator / admin).
- [ ] Порты API и моста не открыты в интернет.
- [ ] Запущен ровно один `run_agent`; на дашборде «runner running», heartbeat обновляется.
- [ ] *Connection*: шлюз не `mock`, тип счёта `demo`, символы найдены.
- [ ] Режим ANALYSIS на 1–2 дня, затем DEMO + Start.
- [ ] Emergency stop проверен на демо.
