# Безопасность

## Секреты

* Пароль торгового счёта, токен моста, `DJANGO_SECRET_KEY` — только в переменных окружения
  (`.env`, секреты Docker/VPS). Они не хранятся в БД и не отдаются API: `/api/connection/` сообщает
  лишь, задана ли переменная.
* `MT5Credentials.__repr__` скрывает пароль; фильтр `apps.audit.logging.RedactSecretsFilter`
  вычищает значения секретов, `password=…`, `token=…` и `Bearer …` из всех логов, а
  `DjangoJournal` — из сообщений журнала и ордеров (покрыто тестами).
* `.env`, `*.pem`, `*.key` в `.gitignore`.

## Доступ к API

* Аутентификация по токену (DRF) или сессии; без роли вход запрещён.
* Роли: **viewer** — только чтение; **operator** — Start/Pause/Stop/Emergency stop, бэктесты;
  **admin** — настройки риска/стратегии/подключения, смена режима, сброс kill switch, закрытие
  позиций агента, аудит.
* Ограничение частоты: вход 10/мин, анонимно 30/мин, пользователь 600/мин.
* Каждая команда, смена режима, изменение настроек, вход и неудачный вход пишутся в `AuditLog`
  (кто, когда, IP, значение до/после).

## Сеть

* `docker-compose.yml` публикует порты только на `127.0.0.1`. Для доступа по сети поставьте
  обратный прокси с TLS и включите `DJANGO_SECURE_HTTPS=true` (secure cookies, HSTS, редирект).
* MT5-мост (`bridge/mt5_bridge.py`): токен ≥ 32 символов (сравнение за постоянное время), белый
  список IP, лимит запросов, только явный список методов, по умолчанию слушает `127.0.0.1`.
  Подключайтесь через TLS, VPN или SSH-туннель; адрес не `https://` разрешён только для localhost.
* **Мост по умолчанию только для демо**: при `BRIDGE_ALLOW_REAL=false` он отклоняет `order_send`,
  если в терминале не демо-счёт — независимо от того, что пришло с сервера.

## Защита торговли

* LIVE невозможен, пока: `ALLOW_LIVE_TRADING=true` на сервере **и** стратегия прошла walk-forward на
  реальных данных **и** терминал сообщает REAL-счёт **и** admin повторно ввёл пароль и фразу
  `ENABLE LIVE TRADING` **и** (для моста) `BRIDGE_ALLOW_REAL=true`. Неизвестный тип счёта = LIVE
  запрещён. Обычные настройки интерфейса режим не меняют. Изменение параметров стратегии сбрасывает
  валидацию.
* Ни один ордер не уходит без одобрения Risk Manager: одобрение подписано HMAC с секретом процесса,
  живёт 10 секунд и привязано к конкретному сигналу, объёму и цене.
* Идемпотентность: детерминированный `signal_id`, запись намерения в БД до отправки, ключ в
  комментарии ордера, проверка брокера перед отправкой.
* Неизвестное состояние (таймаут, разрыв) → новые сделки блокируются до сверки позиций и ордеров.
* Kill switch сохраняется в БД и переживает перезапуск.
* Один процесс агента (advisory lock PostgreSQL) и одна блокировка на все торговые команды.

## Известные риски

* Комментарий ордера может быть изменён брокером; тогда основным источником идемпотентности
  остаётся журнал в PostgreSQL (а при его потере — magic + символ).
* Токен в `sessionStorage` браузера уязвим к XSS; CSP в `deployment/nginx.conf` ограничивает
  источники скриптов. Для многопользовательского доступа рассмотрите SSO/2FA.
* Бэктесты в API запускаются в фоновом потоке веб-процесса; для production вынесите их в очередь
  задач.

Сообщения об уязвимостях — владельцу репозитория, не в публичные issue.
